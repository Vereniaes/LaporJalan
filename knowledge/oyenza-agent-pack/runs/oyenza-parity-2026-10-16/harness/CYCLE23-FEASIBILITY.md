## Conclusion

**No public MapLibre4.7.1 setting was found that restores multisampled building silhouettes on an AAfalse canvas, or switches an existing AAtrue default framebuffer to cheaper per-layer sampling.** The engine has no fill-extrusion analytic-antialias paint property or public default-framebuffer sample-count/resolve switch. A reliable final-cycle fix is therefore not established by source reading.

One small public API experiment remains technically possible without lowering geometry fidelity: higher canvas pixel ratio for city navigation with AAfalse, returning to the existing ratio for explicit close inspection. It is supersampling through a larger drawing buffer and browser display scaling, not MSAA. Its visual benefit and city navigation cost are unmeasured. It is a candidate for a carefully bounded experiment, not a recommendation to spend the remaining correction blindly or a claim that V6 already validates it.

## Source-backed findings

1. **MSAA is fixed at context creation in this version.** Installed `node_modules/maplibre-gl/src/ui/map.ts:123-126,590-591,2974-2996` maps the boolean constructor option to canvas.getContext attributes. Public options offer no sample-count field, and the Map exposes no setAntialias method. Calling Three.WebGLRenderer with a different antialias option cannot change the supplied existing context: Three r170 only creates a context when none was provided (`WebGLRenderer.js:246-250`). Recreating the map/context on mode changes would violate the single-map/lifecycle direction and is not proposed.
2. **Extrusion edges have no material coverage smoothing.** `src/shaders/fill_extrusion.fragment.glsl` simply outputs interpolated lit color; its vertex shader carries position/normal/height/color, not a triangle-edge coverage attribute. The installed style specification supports fill-antialias for flat fill, not an equivalent fill-extrusion property. Applying fill-antialias or line-blur elsewhere will not smooth the raised roof/silhouette edges. Lighting/color/opacity can change contrast, but cannot recreate missing subpixel edge coverage and is not a proven visual correction.
3. **There is one real public pass-count lever, but it is unrelated to this edge problem.** The current building layer uses opacity0.92 (`src/components/Map3D.tsx:335`). Installed `draw_fill_extrusion.ts:24-43` draws such buildings twice: depth then color. Setting opacity1 with no pattern uses one pass. That does not antialias AAfalse edges and changes building appearance relative to the0.92 reference. It also cannot explain the supplied synthetic close-inspection AAon cost if no source buildings are being drawn there. It is not an evidenced fix for the measured default-framebuffer difference.
4. **There is no redundant Three MSAA resolve exposed to remove here.** DamageLayer renders directly to the shared default framebuffer, autoClear false, with no WebGLRenderTarget. In Three r170 `WebGLRenderer.js:1271-1279`, explicit multisample-target resolution runs only for a non-null currentRenderTarget; resetState sets that value null at2825. Thus removing a render-target resolve call would not optimize this application's path. Browser/driver handling of the multisampled default drawing buffer remains outside this public custom-layer API. This source fact does not establish the exact GPU bottleneck; AAon/off timing establishes a setting-sensitive cost, not a traced hardware resolve attribution.
5. **MapLibre FBO support is not a cheap selective city-AA API.** `draw_custom.ts:13-43` permits prerender/custom rendering and restores the shared framebuffer state; ordinary building draws are engine-controlled. `gl/framebuffer.ts` is an internal attachment wrapper without a public multisample policy. `render/render_to_texture.ts` serves terrain render stacks, excludes fill-extrusion from its listed flat layer types, and is explicitly internal. Moving engine city layers into a custom multisampled FBO and recompositing shared color/depth would require render pipeline work, not a small supported setting. No private painter/FBO override, engine patch, postprocess, new renderer, global depth bypass or hidden city fallback is proposed.

Primary versioned references checked: [MapLibre v4.7.1 map options/context creation](https://github.com/maplibre/maplibre-gl-js/blob/v4.7.1/src/ui/map.ts), [fill-extrusion drawing](https://github.com/maplibre/maplibre-gl-js/blob/v4.7.1/src/render/draw_fill_extrusion.ts). Installed source, including Three0.170.0, was the implementation authority. Current upstream API syntax was not substituted for this version.

## Public pixel-ratio option and its limits

`Map.getPixelRatio/setPixelRatio` are public in installed4.7.1 (`map.ts:880-899`); setPixelRatio calls resize. Actual buffer size may be clamped by GPU/canvas limits (`map.ts:867-877`). Increasing from1 to1.5 requests2.25 times as many pixels; from1 to2 requests4 times. This does not reduce vertex/profile detail or change physical dimensions. It can reduce visible stair steps when displayed at the same CSS size, but it does not guarantee the same appearance as MSAA.

A bounded candidate could keep AAfalse, request a modest increased pixel ratio during ordinary city navigation and use the current ratio in explicit inspection. It would preserve one map/context and keep the fast close-inspection raster path, but resize/state transitions and city GPU cost require validation. Readability, labels, popup alignment and<=2CSSpx geometry projection must remain correct after the buffer resize; actual attributes/drawing-buffer dimensions must be recorded, not inferred from browser DPR.

Such an implementation would be a **new application candidate**. Do not alter the browser DPR fixture, baseline screenshots, benchmark threshold or baseline settings to manufacture equivalence. Record the app's deliberate ratio override and freeze new source identity. The existing benchmark exercises synthetic idle/inspection-orbit/inspection-pan at its own specified pose; it does not by itself establish actual-city pan/rotation responsiveness at a larger buffer. A matched navigation observation plus native-size city screenshots on both viewports would be necessary before accepting this visual tradeoff. No measurement was run here.
